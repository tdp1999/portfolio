Surveyed sites with notable mega-menus / nav dropdowns. Three style families emerged:

  • A · icon + text-column Side-icon row with title above description. Used by GitHub, Mintlify, Raycast. Iconography earns its weight when items overlap by name (Settings, Settings & billing, User settings…). For 5 distinct items like ours, the icon is decorative weight — but can be redeemed with tighter typography. (V1)
  • B · centered icon card Icon centered above title, all-center text in a card. Used by Vercel, Cal.com, Notion. Feels premium, doubles per-item height, and works best with bold colored icons + 2-3 cells in a row. With 5 items we'd need a hero row. (V2)
  • C · typography-only No icons. Bold title + 1-line description, or eyebrow + title. Used by Stripe, Linear, Apple docs. Editorial register; fits portfolios that favor type over chrome. Best when descriptions are confident one-liners. (V3, V4)
  • D · hero + list One item gets full-card hero treatment (the Resume CTA), others sit as compact rows. Used by Railway (the original reference — their "Enterprise" panel with the train illustration is the hero, the other items are compact cards). Solves the 5-items-in-2-col problem and signals what matters most. (V5)
  • E · inline-glyph reveal Icon-as-inline-glyph (text-sized, monochrome). Description hidden by default, surfaces on hover. Used by Vue docs, Astro, indie portfolios. Dense, quiet — earns the icon by treating it as a tiny typographic accent rather than a card element. (V6)

NN/g findings worth respecting: (1) mega-menus work because users see options at a glance — don't hide the description for items where it's load-bearing. (2) hover-open is consistently frustrating — click-to-open + click-outside + Esc is the gold-standard. (3) don't take over the whole viewport — keep panel ≤ 560–640px wide for 1-col, ≤ 720px for 2-col with hero.
Approaches explicitly rejected: flag/illustration grid (overkill for 5 utility links), full-bleed slide-down panel (too aggressive for a portfolio), country/locale picker (the language switcher handles this separately).

Every panel on this page (V1–V7d) renders always-open so shapes compare side by side. The real menu is a disclosure: a button that shows/hides a region of links. The survey is unanimous on one point — a nav dropdown is a disclosure, never role="menu" (that role makes screen readers swallow Tab and expect the arrow-key nav meant for app menus like Word).

Rule Behaviour Why
Products column first The featured Products column leads (leftmost); the titled columns follow. The product (Document Engine) is the destination the menu exists to surface — it earns first read.
One product → featured card Screenshot tile + title + description + CTA link ("Explore the engine →"). A single flagship deserves a full preview, not a cramped row.
Two+ products → stacked list The column auto-switches to a compact "Products" list (tile + title per row); no caller change. Driven by the product: true count — the layout scales as more products ship.
Titled columns = icon rows Explore / Documents are framed-icon + label rows. No sub-hints, no badges by default. The labels are self-explanatory; hints and badges are visual noise unless explicitly asked for.
2-col at laptop+ ≥ 1024px the titled columns sit side by side; full sizing (wider tracks, 40px icon frames). Room to breathe where the viewport affords it.
Stack at tablet 768–1023px: the titled columns stack (Documents under Explore); the Products column narrows and gaps pull in. The inline nav still shows the menu down to 768px — stacking keeps it clear of the viewport (no overflow).
Below tablet → sheet < 768px the menu is hidden; the hamburger sheet takes over with the same Products / Explore / Documents groups. One IA, two presentations — the mobile sheet mirrors the desktop grouping.
Screenshot tile + hover mist The product tile is a real screenshot; on hover it thins to a ~70% mist revealing the editor icon. Theme-matched dark/light asset (swapped under .dark). Shows the product working, then hints the mark — no hard swap; each theme gets a shot that blends.
Viewport-centred + hover/click align="screen" centres the panel on the viewport (measured from the trigger on open); opens on hover and click. A wide panel reads best centred; hover + click matches the sibling nav items.
